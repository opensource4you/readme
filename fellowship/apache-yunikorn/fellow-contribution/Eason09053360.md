## Highlight：queue cleaner 刪掉正要放進 application 的 dynamic queue（[YUNIKORN-3539](https://issues.apache.org/jira/browse/YUNIKORN-3539) → [3547](https://issues.apache.org/jira/browse/YUNIKORN-3547) → [3557](https://issues.apache.org/jira/browse/YUNIKORN-3557)）

**簡介**：YuniKorn 在背景定期跑 queue cleaner，把空的 dynamic queue 刪掉。新增 application，或是把已完成的 application 復活（revive）時，cleaner 可能剛好在「找到 / 建立 queue」和「把 application 放進 queue」之間把 queue 刪掉。application 會被放進一個已經不在 queue 樹上的 queue，永遠不會被排程，然後也沒有任何錯誤訊息；如果 queue 還在建立中，cleaner 會因為 `queueEvents` 是 nil 而 panic。

**為什麼會這樣**

1. `AddApplication` 從找到 / 建立 dynamic queue 到加入 application，全程拿著 partition lock，用意就是不讓 cleaner 在中間刪 queue。但 `cleanQueues` 本身從來沒拿這把 lock，所以這個保護根本沒有作用。
2. revive 路徑也一樣：`resolveRevivedQueue` 在 lock 裡找到或重建 queue，但 `RestoreQueue` 和 `queue.AddApplication` 是放開 lock 之後才做的。
3. 修好第 2 點之後還有一個洞：dynamic queue 的 limit（max resource、guaranteed resource、max apps）是從 application 的 tag 讀出來的，只存在 queue 上。cleaner 刪掉空 queue 之後，revive 重建 queue 時不會再讀 tag，重建出來的 queue 就沒有任何 limit。

**修法裡的判斷**

- **[#1206](https://github.com/apache/yunikorn-core/pull/1206)：cleaner 只在「檢查是否為空 + 刪除」這段拿 partition lock**，並在 `PartitionContext` 的 lock 註解寫明這是例外。
- **revive 路徑刻意不在 #1206 一起修**：照當時 `PartitionContext` 註解的規則，拿著 partition write lock 時不能動 application，要修就得重排 revive 的步驟，看起來會動到 YUNIKORN-3218 的設計，所以先在 PR 描述註明不在這次範圍內。review 時 reviewer 指出，這條規則的理由（scheduling 拿著 application lock 再跟 partition 要 node list）從 YUNIKORN-807 之後就不成立了，因為 node lookup 已經不拿 partition lock。[#1214](https://github.com/apache/yunikorn-core/pull/1214) 照這個方向，只把那兩行搬進 lock 裡，不用重排 revive 流程，並把 lock 註解改成現在真正的規則：拿著 application 或 queue lock 的程式不能等 partition lock。
- **[#1218](https://github.com/apache/yunikorn-core/pull/1218)：只有重建 queue 時才套用 tag 的 limit**：把 `AddApplication` 裡處理 tag 的邏輯抽成 `setQueueLimitsFromTags`，只在 revive 真的重建 queue 時呼叫。已存在的 queue 保留原本的 limit（就算原本沒有 limit 也不動），recovery queue 和 managed queue 不受影響。

**怎麼一路追下去的**

- #1206 的 PR 描述先註明 revive 路徑有同樣的問題 → reviewer 請我開 follow-up → YUNIKORN-3547（#1214）
- #1214 的 review 中，另一位 reviewer 指出重建的 queue 會丟掉 tag 的 limit → YUNIKORN-3557（#1218）

**驗證**：#1206 的 `TestCleanQueuesAddApplication` 讓 cleaner 在背景不停跑，同時新增 / 移除 1,000 個 application，沒有修正時會 fail；#1214 的 `TestCleanQueuesReviveApplication` 對 revive 做同樣的事；#1218 用 table-driven 測試涵蓋重建的 queue、既有的 queue、recovery queue 三種情況。
